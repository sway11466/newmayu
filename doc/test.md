# テスト方針

t-wada（和田卓人）さんのテストの考え方を土台にする。

## 目的

テストは、変更を恐れずに進めるためにある。壊したらすぐ気づける状態を保ち、作り直し・リファクタリング・機能追加を安心して続けられるようにする。

newmayu では、テストが mayu/yamy 互換の挙動を固定する役も持つ（[principle.md](principle.md) 1）。テストが通っている限り、互換が保たれていると言える状態を目指す。

## テスト駆動開発（TDD）

Red → Green → Refactor の順で進める。

1. Red — 次に欲しい振る舞いを、失敗するテストとして先に書く。実際に失敗することを確かめる。
2. Green — そのテストが通る最小のコードを書く。
3. Refactor — テストが通ったまま、コードの重複や読みにくさを直す。

バグを直すときも、まずバグを再現するテストを書いて失敗させてから直す。

## 互換のテスト

- 期待値の正解は yamy の挙動。根拠は mayu のマニュアル、yamy の `readme.txt`、yamy のソース（[spec.md](spec.md) の正本と同じ）。
- テストには、元になる `.mayu` の記述をコメントで添える（例 `// key C-H = BackSpace`）。
- 既存テストの期待値を変える・テストを消すのは、挙動を変えることになる。先にオーナーに聞く。

## テストサイズ

テストを、何に依存するかで分ける（Google のテストサイズ。t-wada さんが紹介している分け方）。

- Small — 1 プロセスの中だけで動く。ファイル・OS・時刻に触れない。速く、毎回同じ結果になる。
- Medium — 1 台のマシンの中で、ファイルや別プロセスを使ってよい。

newmayu での置き場所:

| 対象 | サイズ | 実行 |
|---|---|---|
| 字句解析・構文解析（`crates/newmayu/src/config/`）、エンジンの判断（`crates/newmayu/src/engine.rs` の入力 → 出力） | Small | `cargo test` |
| `.mayu` ファイルを読ませる確認 | Medium | `cargo test` |
| 実機テスト `selftest`（フック → エンジン → `SendInput` の通し） | Medium | 手元で `cargo run --bin selftest` |

テストの大半を Small に置く。Medium は Small で確かめられない境目（ファイル、OS の API）だけにする。

`selftest` は `newmayu.exe` を起動し、実行中は物理キーボードもテスト用の `.mayu` で変換される。デスクトップセッションが要るので CI では動かさない。オーナーが把握したうえで実行する。

## テストしやすい設計

- 判断するコードと、OS に触れるコード（フック、`SendInput`、窓、IME、ファイル）を分ける。
- 判断するコードは、OS に触れる所を窓口（trait）越しにして Small で試せるようにする。エンジンの `feed(Input, &mut dyn Os)` がこの形で、テストは出力を記録する窓口を渡す。
- OS に触れるコードは薄くし、判断を持たせない。

## テストの書き方

- テスト名に、確かめる振る舞いを書く（例 `control_h_to_backspace`）。
- 1 つのテストで 1 つの振る舞いを確かめる。
- 準備 → 実行 → 確認の順に書く。
- テストの中に条件分岐やループで期待値を作る処理を入れない。期待値はそのまま書く。
- テストコードもプロダクトのコードとして読みやすく保つ。

## 運用

- `cargo test` が通る状態でコミットする。
- フック・入力の注入・IME・窓まわりに触れる変更では、`selftest` の実行をオーナーに頼む。
- カバレッジ（テストが通ったコードの割合）は、テストの抜けを探す手がかりとして見る。数値を目標にしない。
